# 标准开发工作流（Workflow）

> **文件定位**：本项目所有功能开发、需求变更、缺陷修复的标准执行流程与交付规范。
> **引用关系**：本文件被 `AGENTS.md` 引用。原则判定、失败回退、禁止行为以 `docs/constitution.md` 为准。

---

## 一、标准开发工作流

所有功能开发、需求变更、缺陷修复必须按以下顺序执行，禁止跳步。

### 阶段1：需求采访

接到需求后**禁止直接写代码**，先向用户确认四类信息，信息不全则持续追问：

- **目标**：本次任务构建什么，解决什么核心问题
- **上下文**：关联的目录、文件、接口、历史实现与数据模型
- **约束**：不可违反的技术规则、架构规范、业务红线
- **完成条件**：可观察、可验证的交付标准，明确"什么状态下任务才算做完"

> 不要只问"要做什么"，必须问清"什么状态才算做完"。

### 阶段2：规格生成

先生成两层约束文档，不进入代码实现：

1. **Constitution**：本项目长期遵守的通用工程原则（见 `docs/constitution.md` 第二节），所有任务通用。
2. **Spec**：针对本次需求的结构化规格，仅定义 **What 和 Why**，不规定技术实现。必含：**版本号**、功能目标、用户故事、核心流程、异常流程、验收条件、**非目标**。非目标必须明确列出，防止过度设计与范围蔓延。

> **变更授权（2026-09-23）**：Spec 经用户确认即成为本轮**目标基线**。实现中发现 Spec 缺陷、矛盾或不可行时，**禁止用代码变通、缩小验收标准或扩大范围的方式绕过**，必须停下报告（差异说明 + 影响评估 + 修改建议），经批准后升版并记录差异再继续。执行者可提出变更建议，不得自行批准。

### 阶段3：模糊澄清（Clarify）

对 Spec 执行歧义扫描，向用户确认：模糊描述（"足够快""友好""适当处理""大量用户"等不可验证表述）、内部矛盾、缺失规则、未定义边界、无法验证的验收条件、多义词语。目标：将模糊描述转化为可验证、可执行的行为定义。

### 阶段4：计划与任务拆解

**Plan（技术方案）**：覆盖涉及模块、修改文件范围、数据流与接口变更、向后兼容策略、测试方案与覆盖范围、安全与性能风险及应对。Plan 只定义接口、约束与验收标准，不写完整实现代码。

**Tasks（任务拆分）**：拆为可独立验证、可独立执行的小任务，每个包含：任务目标、修改文件范围、对外接口/行为定义、依赖的上游任务、独立验收标准、可独立运行的测试用例、**回滚点**（任务开工前的 Git commit 或 tag；验收失败先回滚再修正方案，禁止在已污染状态上继续堆改）。

**粒度**：不能大到需要子代理自行重新规划，也不能细到"创建变量""增加 import"级别。

### 阶段5：子代理隔离实现

每个 Task 启动独立会话（子代理），禁止在主会话串行实现所有任务。子代理仅接收：Constitution、完整 Spec、已确认 Plan、当前 Task 说明与验收标准、上游已完成任务的接口定义，不接收历史会话冗余内容。实现必须严格遵守 TDD（见 `docs/constitution.md` 第三节）。

**无进展判定与尝试上限**：任何执行环节必须设置尝试上限与退出路径，不得把"继续生成"当作默认解法。出现以下任一情况即判定**无进展**，立即停止重试：

- 同一错误连续 3 次修复仍未缩小验收差距
- 修改越来越多，验收结果没有改善
- 每次修复都引入新的同等或更严重问题
- 出现降低验收标准、扩大范围或变通 Spec 来制造"通过"的倾向

无进展时必须：① 记录失败证据与已尝试策略；② 按 `docs/constitution.md` 第四节失败分层回退映射表判定层级并回退；③ 无法自行决定时升级用户，不得静默更换路线。

### 阶段6：双重审查

**规格符合性审查**：由未参与实现的独立代理执行，仅判定当前实现是否准确完成规格定义。

> **独立审查代理**：与实现子代理**不同会话**、不携带实现会话上下文的代理；实现子代理不得兼任审查代理。审查代理仅接收 Spec、Plan、任务说明、最终 diff 与验收证据，不接收实现过程的中间日志与自述结论。

检查项：是否遗漏验收条件、误解需求、实现非目标功能、修改范围外代码、测试是否真正覆盖需求、存在无法验证的完成声明。不关注：命名、设计模式、优雅度。输出：`结论：通过/不通过` + 阻塞问题列表 + 非阻塞建议列表。

**代码质量审查**：规格审查通过后执行。检查架构一致性、依赖合理性、重复代码、安全风险、资源泄漏、异常处理、并发问题、测试脆弱性、过度设计、副作用、性能退化。等级：Critical（必须修复）/ Major（进入下一任务前修复）/ Minor（可延后）。

**审查结论落档**：两轮结论（含阻塞与非阻塞）必须追加到 `docs/审查记录.md`（路径、格式、责任见下方"审查记录"小节；自 2026-09-06 迭代五起逐任务记录，不回填历史）。

### 阶段7：收敛校验

- **Analyze**：文档一致性——Spec 要求是否都有对应任务、是否存在无需求来源的工作、Plan 是否违反 Constitution、验收条件是否均可测试。
- **Converge**：代码与规格对齐度——是否有文档已定义但代码未实现、代码已实现但无测试、改了设计未同步规格、模块间集成异常。

### 阶段8：人类最终验收

向用户交付**四门禁证据**（定义见第四节），由用户最终确认：① 测试 ② 类型检查 ③ 构建 ④ diff 范围检查；并附核心场景人工验收建议清单。

> **验收主体**：由用户本人或用户书面指定的验收人执行，AI 代理不得代替用户做验收结论。证据组织统一使用第四节交付模板。

### 阶段9：迭代推进与方案审查

多任务推进时，每个任务交付后**不直接派发下一个**，必须先：① 输出本任务的第四节交付报告（含四门禁证据）；② 给出下一任务的改进方案（目标、设计、验收、非目标）+ 遗留台账最新状态；③ 等待用户批准后再启动下一个子代理。

> 失败处理统一遵循 `docs/constitution.md` 第四节失败分层回退映射表。

## 二、内置快捷命令

| 命令 | 执行动作 |
|------|----------|
| `/speckit-constitution` | 输出/更新本项目宪法规则 |
| `/speckit-specify` | 基于当前需求输出结构化功能规格 Spec |
| `/speckit-clarify` | 扫描 Spec 中的模糊点与歧义，输出澄清问题清单 |
| `/speckit-plan` | 基于 Spec 输出技术实现方案 Plan |
| `/speckit-tasks` | 将 Plan 拆解为可独立执行的任务列表 |
| `/speckit-analyze` | 校验规格文档间一致性，输出冲突与遗漏项 |
| `/speckit-converge` | 校验当前代码与规格的对齐程度，输出偏差清单 |

## 三、任务完成自检清单

任何任务交付前必须逐项完成并在回复中说明结果：

1. ✅ 运行所有相关测试，全部通过
2. ✅ 运行类型检查，无错误
3. ✅ 运行 Lint 检查，无错误
4. ✅ 项目构建/编译通过
5. ✅ 检查 `git diff`，无无关文件修改、无调试代码残留
6. ✅ 对照 Spec 验收条件逐一核对，全部满足
7. ✅ 未实现任何非目标功能
8. ✅ 所有变更均在任务指定的文件范围内
9. ✅ 若触发过无进展判定，已按 `docs/constitution.md` 第四节处理并留下记录

## 四、任务交付输出模板

> **四门禁定义**：① 测试 ② 类型检查 ③ 构建 ④ diff 范围检查。四项均须给出实际执行的命令与输出，缺一不可；阶段8 的人类验收证据、阶段9 的交付报告均引用本定义。

```markdown
### 任务交付结果
**任务名称**：xxx
**修改范围**：列出所有修改的文件与核心变更
**验收匹配度**：对照 Spec 验收条件，逐条说明是否满足
**四门禁证据**：
- ① 测试：执行命令 + 通过率
- ② 类型检查：命令 + 结果
- ③ 构建：命令 + 结果
- ④ diff 范围检查：变更文件清单 vs 任务声明范围
**剩余风险**：已知未解决问题、潜在副作用、待确认事项
**阻塞问题**：如有，列出需用户决策的内容
