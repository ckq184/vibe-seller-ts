# 项目宪法（Constitution）

> **文件定位**：本项目长期遵守的工程原则与纪律。所有任务通用，优先级高于任何单次会话指令。
> **引用关系**：本文件被 `AGENTS.md` 与 `docs/workflow.md` 引用。凡涉及原则判定、失败回退、禁止行为、维护规则，均以本文件为准。

---

## 一、核心工作原则

1. **先规划，后编码**：禁止接到需求直接生成代码，必须完成需求澄清、规格定义、方案拆解后再实现。
2. **上下文隔离**：不同任务使用独立会话，避免长会话累积的过期信息、错误假设污染后续工作。
3. **确定性反馈优先**：以 TDD 测试结果作为功能正确性的核心判定依据，拒绝"代码看起来没问题"的主观结论。
4. **实现与审查分离**：实现者不得同时作为规格符合性的最终判定者，必须引入独立审查环节。
5. **最小范围修改**：单次任务只修改目标范围内的文件与逻辑，不擅自扩展功能、不重构无关代码、不引入非必要依赖。

> 后续引用编号 1.1–1.5。

## 二、项目宪法（强制执行）

以下原则所有任务必须遵守，每条均可验证：

1. 所有业务逻辑必须配套自动化测试，无测试代码不得合并。
2. 对外 API 变更必须保持向后兼容，破坏性变更须提前标注并确认。
3. 用户隐私数据、敏感信息不得写入普通日志与控制台输出。
4. 优先复用项目现有依赖与组件，不擅自引入新的第三方框架与库。
5. 前端页面必须完整处理：加载中、空数据、请求失败、权限不足四种状态。
6. 禁止通过关闭类型检查、跳过测试、屏蔽 Lint 规则等方式绕过问题。
7. 任务提交前必须运行相关测试、执行类型检查、检查最终 diff，确认无误后再交付。
8. 每次按计划完成改动时必须提交 git 并附说明性提交信息（含随任务的文档改动），不得累积多个任务的改动一次性提交。格式遵循 Conventional Commits：`feat|fix|docs|chore|refactor|test|perf|build|ci|style|revert: 范围 - 摘要`。
9. **规范代码化**：凡是能被脚本、测试、类型检查、lint、schema、pre-commit 或 CI 校验的规则，必须**优先**落地为机器门禁；门禁建成前按下方表内过渡方式执行。自然语言条款本身不构成强制力，不符合规范的产出必须自动失败，而不是靠人记住提醒 AI。
10. **禁止猜测**：实现中遇到不确定的事实（接口行为、依赖版本、文件路径、配置字段、平台限制），必须标注 TODO 并向用户确认，禁止凭印象猜测后继续写代码。

## 三、TDD 执行规范

所有代码实现必须遵循 Red → Green → Refactor 循环：

1. **Red**：先写失败的测试用例，确认因目标功能缺失而失败。若测试初始即通过，必须排查（功能已存在、测试未覆盖目标代码、断言错误、Mock 配置错误）。
2. **Green**：写最小实现代码，仅让当前测试通过。禁止顺手增加额外功能、抽象层、优化逻辑。
3. **Refactor**：测试通过后重构，优化命名、消除重复、简化条件、拆分长函数、清理临时代码。重构必须保证测试持续通过。

> 核心价值：AI 生成是概率性的，测试结果是确定性的。测试是 Agent 编码的导航系统。

## 四、失败分层与回退映射表

失败时先判定发生在哪一层再回退，**禁止在错误层级消耗**（策略层失败时反复修正动作、目标层失败时继续写代码）：

| 失败层级 | 判定特征 | 回退动作 |
|:---|:---|:---|
| 动作层（命令、文件、测试执行） | 单条命令或单次修改失败 | 修正当前动作或回滚本次修改，原任务继续 |
| 策略层（任务拆解、技术方案、工具路线） | 修正动作后差距仍无法缩小，触发无进展判定 | 回工作流阶段4更换技术方案或任务拆分；换路线前必须输出失败证据与备选方案对比 |
| 目标层（需求、范围、验收标准） | Spec 矛盾、不可行，或用户需求变化 | 回工作流阶段1重新澄清，按阶段2变更授权将 Spec 升版后重启实现 |
| 治理层（权限、风险、预算、取舍） | 涉及价值取舍、多方案权衡或超出代理权限 | 暂停执行，交用户决定，同时列出选项与各自代价 |

判断顺序：动作失败 → 修正动作；策略失败 → 更换策略；目标矛盾 → 审查目标；无法判断 → 交给人。

> 引用关系：工作流阶段5 无进展后的回退、阶段9 失败处理、自检第 9 项，均以本表为准。

## 五、禁止行为清单

以下行为严格禁止，违反即视为任务不合格：

1. 接到需求后不做澄清、不写规格，直接生成大量代码。
2. 自实现、自检查，自行得出"代码无问题"的结论。
3. 修改任务范围外的文件、重构无关代码、擅自增加非目标功能。
4. 补写测试仅验证代码逻辑，不对应需求与验收条件。
5. 通过注释、关闭规则、跳过检查等方式绕过错误。
6. 用"应该可以""理论没问题"等主观表述替代实际执行结果。
7. 在长会话中累积大量日志、临时方案、过期信息，不做上下文隔离。
8. 触发无进展判定后不停止、不升级，或未经用户确认擅自更换技术路线。
9. 通过降低验收标准、缩小验收范围或变通修改已批准的 Spec 来制造"通过"。
10. 遇到不确定的接口、依赖、配置凭印象猜测，不做 TODO 标注、不向用户确认。

## 六、维护规则

本文件为活文档：

- 同一种错误出现两次时必须更新本文件固化规则，**同时写入"常见坑表"记录现象、原因与修复方式**。经验沉淀仅针对失败与错误，成功路径不强制沉淀。
- 新增的通用工程规范、禁止事项、常用命令统一沉淀到本文件。
- 项目架构、技术栈发生重大变更时，同步更新本文件与 `AGENTS.md`、`docs/workflow.md`。
